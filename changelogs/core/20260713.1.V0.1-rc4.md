# v0.1 RC4

**Release:** 20260713.1.v0.1-rc.4

---

## Summary

### Added

#### Event scopes

Added `scope` to `CoreEvent`.

```ts
scope: "core" | "app"
```

Event scopes define whether an event belongs to the Core runtime or to the application layer.

This allows listeners to filter low-level runtime events while always keeping application events visible.

> **Note**
>
> Custom events currently require the scope to be declared manually.
> A future UX layer will automatically assign the correct scope.

---

#### Runtime event origin

Added `origin` to `RuntimeCoreEvent`.

```ts
origin: "core" | "app"
```

Origin is automatically resolved during runtime event creation.

It identifies whether the emitted event comes from:

- a builtin Core event
- an application-defined event

This information is intended for renderers, debugging and future plugin support.

---

#### Event channels

Introduced the new channel declaration system.

New types:

- `CoreEventsChannel`
- `CoreEventsChannelsShape`
- `FinalEventsChannels<TChannels>`

New global generic:

- `TChannels`

Channels are now:

- declared
- validated
- strongly typed

The builtin `default` channel is always available.

---

#### Channels builder

Added `ChannelsBuilder`.

Responsibilities:

- builtin/custom merge
- duplicate validation
- channel initialization

---

#### CoreEventError

Added a dedicated runtime exception used by the event system.

Events with level:

- `error`
- `fatal`

now throw a `CoreEventError`.

The exception already contains the rendered (and translated when applicable) message.

---

#### Static factories

All Core classes now expose:

```ts
private constructor(...)
public static create(...)
```

The architecture is now ready for future `createTest()` factories.

---

#### Runtime split

Split the previous Runtime service into:

- `RuntimeManager`
- `RuntimeService`

Responsibilities are now clearly separated between:

- runtime state ownership
- runtime context exposition

---

## Changed

### Event listeners

Output listeners have been redesigned.

Handlers now receive:

- the runtime event
- a rendering context

The rendering context currently exposes translation utilities and is designed to be extended.

---

### Listener rendering model

Listeners are now pure renderers.

Instead of performing console output directly they return:

```ts
string | undefined
```

The `EventsManager` is now responsible for:

- console output
- runtime throws
- final output dispatch

Returning `undefined` suppresses terminal output while still allowing side effects such as file logging.

This enables:

- console only
- logger only
- console + logger
- multiple independent renderers

without changing the Core.

---

### Event dispatch

The dispatcher has been completely rewritten.

Dispatch is now performed through declared channels.

Each listener may specify:

- channel
- minimum level
- minimum scope

Filtering is performed before the renderer is called.

Renderers no longer perform their own filtering.

---

### Console integration

`CoreConsoleService` now registers itself using channel policies.

Example:

```ts
registerSystemListener("*", {
    handler,
    channel: "default",
    level,
    scope
})
```

The console no longer filters runtime events.

Filtering is entirely delegated to the `EventsManager`.

---

### Runtime event creation

Runtime events are now automatically enriched with:

- runtime id
- timestamp
- origin

during creation.

---

### Error handling

`CoreError` is now exclusively reserved for initialization failures occurring before the event system becomes available.

Known runtime failures now always go through the event system.

Unknown exceptions are no longer wrapped.

The original stack trace is preserved to simplify Core debugging and bug reporting.

---

### Context architecture

The runtime context has been reorganized.

Managers remain available at the root level.

Other runtime families are now grouped by responsibility.

Current structure:

- managers
- providers
- helpers
- services
- api
- settings

This better reflects the internal architecture of the Core.

---

### Runtime APIs

Public runtime APIs have been separated from internal services.

New categories:

- `api`
  - console
  - developer API

- `services`
  - runtime
  - snapshot
  - tools

---

### Generic usage policy

Generic propagation has been redesigned.

Managers remain fully generic.

API components also remain generic because they expose runtime-aware operations to developers.

Providers, helpers and internal services no longer use class-level generics.

Whenever required, generics are now localized at the method level.

This greatly simplifies maintenance while preserving runtime typing.

---

### Partial contexts

Partial contexts have been introduced at the typing level.

Current implementation focuses on reducing dependency surfaces and improving maintainability.

Runtime still receives the complete context.

Runtime partial injection will be addressed in a future iteration.

---

### Public exports

Added several new public exports.

This includes:

- enums
- event types
- channel types
- runtime helper types

required by the new runtime architecture.

---

## Removed

### Context ready flags

Removed:

- `ctx.ready.*`

Initialization order is now fully guaranteed by `CLI`.

The additional runtime readiness state became unnecessary.

---

### Legacy async throw workaround

Removed the previous async error workaround.

The Core now relies on native JavaScript exception propagation through `CoreEventError`.

---

## Architecture

This release finalizes the runtime architecture introduced during the RC3 cycle.

The Core now clearly distinguishes:

- Providers
- Helpers
- Managers
- APIs
- Services

Each family now follows explicit rules regarding:

- contexts
- generics
- runtime responsibilities

These rules become the architectural foundation for future releases.

---

## RFCs

Impacted RFCs:

- Runtime Event System
- Event Channels
- Runtime Context
- Runtime Error Handling
- Core Initialization
- Generic Propagation Rules

---

## Notes

This release focuses on stabilizing the Core architecture rather than introducing new user-facing features.

The new runtime model prepares the project for:

- logger implementation
- WSC integration
- `createTest()` factories
- plugin architecture
- future v0.2 development

From this point onward, the Core runtime architecture is considered mature enough to serve as the long-term foundation of the project.
